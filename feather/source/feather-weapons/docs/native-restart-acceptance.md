## Exact scope

This developer-only workflow tests two sequential PREPARED GRACEFUL restarts: the full RedM server process, then the dedicated database Windows service MariaDB while RedM remains running. It is not a hard process kill/power-loss test and does not race an economic transaction against COMMIT. Real lost-COMMIT-reply and uncommitted provider-worker-death tests were accepted separately. Do not combine these different boundaries into an unsupported crash-durability claim.

Preparation automatically discovers Jane/John by their stable character IDs, performs their normal seal/restore transitions to settle wear/ammo and saves complete challenged SQL/client baselines in native-restart-report.json BEFORE dispatching the diagnostic preparation. Both players must remain idle with weapons holstered: no firing, movement, item transfers, maintenance or equipment changes until completion.

Inventory then durably journals native-restart-probe.json and atomically creates ONE abandoned reservation on isolated diagnostic scope IDs plus queues redelivery of an ALREADY recorded Lasso229 projection using its original key/payload. It never moves/grants an item or creates synthetic weapon provenance. Only these diagnostic operation IDs are held from background settlement until the boundary is observed. Other recovery continues normally. The reservation is deliberately abandoned, not an in-flight economic body. No preparation replay or automatic fixture repair is permitted after interruption/failure.

A server-process token lives in a runtime convar across resource restarts and changes after a full process restart; resource-only restarts cannot pass. The database case requires an observed SQL outage plus MariaDB Uptime lower than the saved high-water mark, while RedM retains the same process token. A network interruption alone cannot pass. Process tokens are diagnostic witnesses, not security credentials; do not configure feather_restart_process_token in startup cfg files.

Normal recovery must roll back/release the diagnostic reservation and acknowledge the original delivery without adding provenance. Verification compares original event IDs and unique ledger records, healthy move/delivery/refresh queues, unchanged SQL inventory/metadata/revisions/equipment/ammo and logical native ownership/wear. Full-server sessions must be fresh; expected session/epoch changes are excluded from conservation comparison. Other conservation differences stop for review; no repair is attempted. Waiting for characters/recovery is read-only and can be checked again safely. Saved evidence prevents repeat preparation or baseline replacement.

The existing console-enabled gameplay switches might otherwise disappear on full restart. The settings command explicitly restores only the12 whitelisted saved boolean gameplay switches, after a new server process and while clients are disconnected.
